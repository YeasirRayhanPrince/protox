# Own the control plane, adopt the agent loop

**Build only the DB-specific control plane, and adopt the agent loop rather than writing it.** No existing agent harness, from Claude Agent SDK and OpenHands to LangGraph, Inspect, OpenEvolve and AIOpsLab, provides four things the problem depends on. The first is a single dollar ledger that covers LLM tokens, clone and replay compute, and agent-provisioned infrastructure. The second is a scheduler that rations a small, stateful pool of clones and measurement slots. The third is environment transitions that cannot simply be re-run (DDL, restarts, re-clones). The fourth is a provenance split between estimated and measured evidence. These four are the research contribution and the part that has to be safe, so they must sit outside any framework, where an agent cannot get around them. Everything else is commodity: tool calling, subagents, context compaction, caching and permission hooks. The recommendation is to adopt the **OpenHands Software Agent SDK** as the primary baseline loop (event-sourced, replayable, multi-LLM), keep the **Claude Agent SDK** as a frontier-model and safety-hook comparison arm, and own a **minimal mini-swe-agent-style loop** for RL on Gen-DBA. All three should reach the database only through one typed **DB-ACI** served over MCP. This is not hedging. 2026 preprints show that a model RL-trained inside one harness overfits to that harness, and that training across harness variants largely fixes it. Several interchangeable loops are therefore what makes the system co-trainable. The problem itself should be defined as a **budgeted, multi-fidelity, constrained POMDP with options-structured actions and a separately specified shield**. Environment mode (clone, shadow, prod, clone→prod) and guardrail level (G0–G3) are *exogenous experimental factors*, and the formalization keeps Gen-DBA's six moves and four provenance labels unchanged and adds a fidelity label. The survey work supports this: prior tuners and LLM DBA agents cover only three islands of a twelve-family lever space, never under SLOs and a joint dollar-and-hours budget. That gap, together with four others the notes surface, is where the paper's contribution lies.

Treat every tagged claim as a lead to verify, not as an established fact.

## Prior tuners and LLM agents cover three islands, never under SLOs and a joint budget

The non-LLM literature divides into three islands, and each runs as its own loop. **Knob tuners** (OtterTune, CDBTune, QTune, ResTune, OnlineTune, HUNTER, LlamaTune, DB-BERT) optimize only runtime parameters, using measured runs of a fixed or replayed workload. Most of the field's contributions are about sample efficiency and transfer because a single run takes minutes and often a restart. OnlineTune is the main exception that tunes a live instance. It argues that tuning on copied instances is "expensive, delayed, and unsafe", and it reports **91.0–99.5% fewer unsafe recommendations** through contextual BO with a black-box plus white-box safety assessment ([arXiv 2203.14473](https://arxiv.org/abs/2203.14473)). **Index and plan systems** split by signal. Cost-model advisors (AutoAdmin/DTA and RL advisors such as SWIRL, whose reward is believed to be a what-if estimate†) are cheap but inherit estimation error. The production systems found that estimates alone are not enough. Azure SQL verifies every automatic change against measured workload performance and reverts it if there is no gain, with **validation windows of 30 minutes to 72 hours**, and it ships CREATE_INDEX *off* by default ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview)). Oracle creates candidate indexes invisible and keeps them only if test execution shows improvement ([Oracle 19c](https://docs.oracle.com/en/database/oracle/oracle-database/19/admin/managing-indexes.html)). Learned optimizers (Bao, Balsa, Lero, AutoSteer) learn from measured latency but tune only plans. **Layout and maintenance** belongs to the lakehouse vendors. Databricks Predictive Optimization runs OPTIMIZE, VACUUM and ANALYZE and can choose liquid-clustering keys ([Databricks docs](https://docs.databricks.com/aws/en/optimizations/predictive-optimization)), and Snowflake reclusters around a key the user supplies ([Snowflake docs](https://docs.snowflake.com/en/user-guide/tables-auto-reclustering)).

The academic "holistic" tuners stop at the edge of the DBMS. Proto-X tunes knobs, hints and indexes jointly through synthesized proto-actions and reports **up to 53% over the next-best approach** ([PVLDB 17](https://vldb.org/pvldb/vol17/p3373-zhang.pdf)). UniTune argues that joint tuning beats standalone tuning ([arXiv 2303.05710](https://arxiv.org/pdf/2303.05710)). UDO separates heavy from light parameters and uses delayed-reward optimization ([arXiv 2104.01744](https://arxiv.org/pdf/2104.01744)). The finer details of how UDO and UniTune coordinate are [PK] in the notes. All of these optimize measured runtime of a benchmark workload on a dedicated instance. None includes safe online application, rollback of a joint configuration, drift handling, or levers in middleware, the application or infrastructure. Van Aken et al.'s real-world Oracle study warns that benchmark-only, local-storage evaluations on open-source engines overstate how much is automated ([PVLDB 14](https://www.vldb.org/pvldb/vol14/p1241-aken.pdf)). OtterTune shut down in 2024, but that is documented only by a search snippet, and Pavlo's retrospective gives no technical post-mortem ([Pavlo 2024](https://www.cs.cmu.edu/~pavlo/blog/2025/01/2024-databases-retrospective.html)). Any argument that "knobs alone aren't enough" drawn from it is therefore inference.

LLM tuners went from using the LLM as a knowledge source for BO (GPTuner, [arXiv 2311.03157](https://arxiv.org/abs/2311.03157)), to the LLM writing whole configuration scripts (λ-Tune, [arXiv 2411.03500](https://arxiv.org/abs/2411.03500)), to closed-loop agent harnesses. The two closest to this problem are both 2026 preprints. **AgenticDB** jointly tunes DBMS and OS parameters with an Initializer, Planner, rule-based Validator, Executor, Recovery and Auditor. It reports **118.1% average gain over the best baseline**, at **$0.26–$4.80 of LLM spend per workload** under a **100-minute wall-clock cap** ([arXiv 2606.20318](https://arxiv.org/html/2606.20318)). **EvoTune** tunes rewrites, query-level knobs, pg_hint_plan hints and indexes with a 30-hour budget. It reports **2.1× better time-to-target than Proto-X on TPC-H** ([arXiv 2607.17841](https://arxiv.org/html/2607.17841)), which matters directly to this team. Two lessons follow. First, wall-clock benchmarking, not tokens, is the binding budget: a few dollars of LLM spend against 100 minutes of measurement. Second, every one of these systems validates on a benchmark replica with rule-based guards, and none handles SLO-aware deployment.

Diagnosis-and-repair agents do worse once they must act. On **DBA-Bench** (106 live PostgreSQL scenarios, 2026 preprint), the best automated **Safe Pass is 17.9% against 93.4% for a human DBA**. **62.1%** of runs that pass diagnosis fail the outcome check, and **36.7%** of runs that pass the outcome check fail the safety check. A plain ReAct loop on GPT-5.5 beat D-Bot, which cost **$7.16 per run, 7× ReAct's cost for a worse result** ([arXiv 2607.22165](https://arxiv.org/html/2607.22165v1)). The fetched text of DBA-Bench has an internal inconsistency in its difficulty-split numbers, so quote only the headline figures. Microsoft's own study of GPT-5 as an index advisor finds that best-of-5 sometimes beats DTA, but that the first or median answer underperforms on more than half of 127 queries. It also finds that validation by materializing indexes can cost more than the tuning itself ([arXiv 2603.09181](https://arxiv.org/abs/2603.09181)). The variance detail comes via a secondary review. Products stay advisory. DBtune keeps a human in the loop ([DBtune](https://www.dbtune.com/docs/overview)), the Xata Agent repo was archived in June 2026 ([GitHub](https://github.com/xataio/agent)), and pganalyze's Lukas Fittl argues that agents cannot own outcomes ([pganalyze](https://pganalyze.com/blog/the-ai-dba-dilemma)). Two design rules follow, and they carry into the decision below: use good tools and verification rather than elaborate reasoning scaffolds, and close the verification loop inside the harness rather than trusting the agent.

| Coverage island | Representative systems | Signal | Where it runs | What it leaves out |
|---|---|---|---|---|
| Knobs | OtterTune, CDBTune, ResTune, OnlineTune, LlamaTune | measured | offline clone; OnlineTune live | everything but knobs |
| Indexes + plans | DTA, Azure SQL, Oracle Auto-Index, Bao/Lero/AutoSteer | what-if estimate, plus measured validation in products | offline, or live with revert | layout, maintenance, middleware |
| Layout + maintenance | Databricks PO, Snowflake auto-clustering | internal, undocumented | managed background | knobs, plans, OLTP |
| Holistic (3–4 DBMS-internal dims) | Proto-X, UDO, UniTune, EvoTune, AgenticDB (+OS) | measured | benchmark replica | SLOs, $ budget, prod safety, middleware/app/infra |

## One umbrella with twelve lever families on a reversibility spine

The two taxonomy notes describe one lever space from opposite ends. The engine-side note lists C1–C10 (layout, schema, statistics/plans, maintenance, concurrency, pooling/routing, caching, workload management, application shape, features/versions). The infrastructure note lists A–H plus X1/X2 (OS, storage, compute shape, elasticity, topology, data layout, table maintenance, lifecycle, engine/format choice, cost metering). They overlap in two places, data layout (C1 = F) and background work (C4 = G). Merged, they form one umbrella in which the **classic trio is three cells, not three categories**. Indexes are a data-organization lever, hints are a plan-control lever, and knobs are an engine-runtime lever. The umbrella has two axes. The first is *where the lever lives*: infrastructure, service provisioning, engine, middleware or application. The second is *what it acts on*: data organization, optimizer information, background work, concurrency, connections, admission, request shape, capacity or lifecycle. The diagnosis literature shows why the second axis matters. D-Bot's root-cause categories include "Harmful Background Tasks" and "Concurrency Workloads", but its action set is only rewrite, knob and index, so it can diagnose problems it cannot fix ([D-Bot](https://ar5iv.labs.arxiv.org/html/2312.01454)).

| # | Family (merged from) | OLTP example | Warehouse / lakehouse example | Change mechanism | Tier (see formalization) |
|---|---|---|---|---|---|
| U1 | **Data organization** (C1, F; *contains indexes*) | partitioning, MVs, fillfactor/HOT, sharding ([Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)) | sort/cluster/Z-order/liquid keys, file size, Parquet row-group/codec ([Iceberg](https://iceberg.apache.org/docs/1.8.0/maintenance)) | DDL or billed data rewrite | T2 (index) → T4 (shard, engine switch) |
| U2 | **Logical schema & data model** (C2) | denormalization, type changes (rewrite) | — | DDL + app deploy | T3–T4 |
| U3 | **Optimizer information & plan control** (C3; *contains hints*) | extended statistics, plan baselines, pg_hint_plan hint table | column stats/NDV, data-skipping stats | ANALYZE / baseline API | T1–T2, instantly reversible |
| U4 | **Engine runtime & features** (C10; *contains knobs*) | knobs, JIT, parallel workers, extensions | warehouse feature flags (e.g., QAS) | reload / restart / upgrade | T2 → T4 (major version) |
| U5 | **Background work & maintenance** (C4, G) | autovacuum, REINDEX CONCURRENTLY, checkpoints | compaction, manifest rewrite, snapshot expiry | config + scheduled jobs | T2; **snapshot expiry/VACUUM is T4** |
| U6 | **Concurrency & transaction design** (C5) | isolation, lock/idle timeouts, SKIP LOCKED, key scheme | commit-conflict policy vs streaming writers | config + code | T2 (timeouts) → T4 (key scheme) |
| U7 | **Connection, routing & replication middleware** (C6) | PgBouncer mode/size, read/write split, proxy routing ([PgBouncer](https://www.pgbouncer.org/features.html)) | catalog choice (commit throughput) | proxy config / deploy | T2–T3 |
| U8 | **Caching & reuse** (C7) | Redis/coalescing, result cache | disk cache / Alluxio | app/infra config | T2, with miss-storm risk |
| U9 | **Workload management & admission** (C8) | Resource Governor, role limits, backfill rate limits | Redshift WLM, Snowflake queue timeouts | config | T2 |
| U10 | **Application request shape** (C9) | N+1 → eager load, keyset pagination, batching, retries | query rewrites at source | code deploy | T3 (or middleware substitute) |
| U11 | **Capacity, elasticity & placement** (B, C, D, E) | instance family/size, replicas, Aurora min/max ACU, scale-to-zero | warehouse size, multi-cluster, slots/RPUs, price-performance target | API call, restart or failover | T2–T3 |
| U12 | **Host OS & storage** (A, B) | THP, hugepages, I/O scheduler, gp3/io2 IOPS ([AWS EBS](https://docs.aws.amazon.com/ebs/latest/userguide/general-purpose.md)) | mostly inaccessible on managed services | sysctl / volume modify | T2–T3 (EBS modification cooldown [K]) |
| U13 | **Data lifecycle & tiering** (H) | partition detach/drop, retention | TTL, S3 lifecycle, BigQuery long-term storage [K] | policy | T2 (archive) → T4 (delete) |

Three cross-cutting attributes belong to every lever and should be fields in the action schema, not extra families. The first is **delegation mode**: does the agent set the knob directly, or set a *policy* for a managed optimizer? In 2026 the agent often does the latter, for example a Redshift Serverless price-performance target from 1 to 100 ([AWS](https://docs.aws.amazon.com/redshift/latest/mgmt/serverless-capacity.html)), or Snowflake Adaptive Warehouses, which remove size and suspend settings entirely ([Snowflake](https://docs.snowflake.com/user-guide/warehouses-adaptive)). The second is the **cost-metering model** (X2): per second provisioned, per TiB scanned, per slot-hour, per I/O, per byte compacted. The same clustering action can cut the bill under BigQuery on-demand and barely change it under provisioned billing ([BigQuery editions](https://docs.cloud.google.com/bigquery/docs/editions-intro)). The third is **engine and format choice** (X1), which constrains everything else. One example is that Iceberg v3 cannot be downgraded and v2 readers cannot read it ([AWS Redshift docs](https://docs.aws.amazon.com/redshift/latest/dg/iceberg-v3-features.html)). Financial commitments (reserved instances, slot commitments) are a degenerate lever: they have no performance effect, cannot be undone, and should always be T4.

What makes the umbrella *holistic* rather than a list is the interactions. Long transactions (U6) block vacuum (U5), which bloats tables (U1) and degrades plans (U3). Transaction pooling (U7) rules out session-level SET knobs (U4) and SQL PREPARE (U10). Replicas with hot_standby_feedback (U7/U11) hold back vacuum (U5). Plan baselines (U3) can hide new indexes (U1). Minimum serverless capacity (U11) bounds the buffer pool (U4), so scaling down evicts the cache. An agent that sees only one family repeats the D-Bot failure: it diagnoses correctly and acts on the wrong layer. Many [doc]/[K] items in the source notes (PostgreSQL, MySQL and vendor documentation cited from memory) are standard references, but the specific numbers flagged [K] need spot-checking before quoting. These include the Iceberg 512 MB default target file size, the EBS modification cooldown, and the guidance that Aurora I/O-Optimized pays off above roughly 25% I/O spend. *Naming note:* the Gen-DBA "Storage Layout Optimization" task ([cidr27_gendba.md](../docs/cidr27_gendba.md) §2.1) sits inside U1 (and U13 for Parquet file layout).

## The problem is a budgeted, multi-fidelity constrained POMDP with a switchable shield

**Resolve the naming clash first.** In `cidr27_gendba.md`, **SLO means Storage Layout Optimization**, one of the three learning tasks (QO, SLO, CE). In this problem, SLO means **Service Level Objective**, and the SRE vocabulary that comes with it (error budgets, freeze policies) does real work in the formalization. A paper that uses both will confuse reviewers. Reserve "SLO" for service objectives and rename the Gen-DBA task "SL" or "layout optimization" in any joint paper.

No single framework covers the problem, but five standard ones compose cleanly. SLOs and error budgets are **CMDP** constraints on cumulative auxiliary cost ([Achiam et al., ICML 2017](https://proceedings.mlr.press/v70/achiam17a.html)). Guardrails are a **shield**, a component specified separately from the policy that blocks or corrects actions. Its key property for this work is that it can be switched on and off while the policy stays fixed ([Alshiekh et al., AAAI 2018](https://ar5iv.labs.arxiv.org/html/1708.08611)). Clone versus prod is **multi-fidelity, cost-aware optimization** ([MF-GP-UCB](https://arxiv.org/abs/1603.06288v4)). Heavy actions such as index builds and resizes are **options/semi-MDPs** with delayed effect ([Sutton, Precup, Singh 1999](https://people.cs.umass.edu/~barto/courses/cs687/Sutton-Precup-Singh-AIJ99.pdf)), which matches UDO's heavy/light split. Diagnosis is **partial observability**: the bottleneck is latent, and ORIENT and SCREEN are information-gathering actions that cost something. The POMDP framing is a modelling choice; the notes found no DB-specific POMDP paper.

### State, observation and the two labels on every value

The system under optimization is the full stack: engine, data, middleware, application touchpoints and provisioned infrastructure. Its latent state is $s_t = (x_t, D_t, w_t, z_t)$. Here $x_t$ is the configuration vector over families U1–U13, $D_t$ the data state, $w_t$ the workload regime (which drifts), and $z_t$ the latent bottleneck. Every observed value carries **two labels**. The first is Gen-DBA's provenance $\pi \in \{\text{measured}, \text{estimated}, \text{derived}, \text{declared}\}$ ([training_record.md](../docs/training_record.md) Rule 1). The second, new, is a **fidelity** $\phi \in \{f_0\ \text{cost model},\ f_1\ \text{surrogate},\ f_2\ \text{clone+replay},\ f_{2s}\ \text{shadow},\ f_3\ \text{prod}\}$. The second label is needed because "measured on a clone" is not "measured on prod". The notes list the sources of the gap: clone hardware differs from prod (Oracle's own replay case found a CPU-sizing cause, [Oracle blog](https://blogs.oracle.com/coretec/testing-with-oracle-database-replay)), copy-on-write clones start with cold caches, SPA-style replay is serial and isolated and so misses contention ([Oracle RAT](https://www.oracle.com/a/otn/docs/enterprise-manager/ds-19c-oracle-real-application-testing.pdf)), some statements cannot be replayed (pgreplay drops COPY, [pgreplay](https://raw.github.com/laurenz/pgreplay/PGREPLAY_1_3_0/README)), and data drifts between snapshot and action. Clone substrates have hard limits: Aurora allows **15 copy-on-write clones before falling back to full copies** ([AWS](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)), while Neon/Lakebase branches appear in about a second ([Databricks](https://docs.databricks.com/aws/en/oltp/projects/autoscaling)). *Shadow* ($f_{2s}$, mirrored live traffic against a replica) is included for completeness, but the notes researched no shadow-traffic tooling, so its properties are still to be established. The fidelity label sharpens the team's own finding. PostgreSQL's cost model **understated the benefit of the same index set by roughly 2×, twice** (−17.8% estimated vs −41.6% measured), which is exactly the difference between $f_0$ and $f_2$ ([training_record.md](../docs/training_record.md)).

### Actions are the six moves, typed

The action space maps one-to-one onto the six moves in [dba_loop.md](../docs/dba_loop.md), so every harness event can be attributed to exactly one move, which is invariant 1 of the record:

| Move | Action class | Fidelity / provenance | Formal role |
|---|---|---|---|
| 1 ORIENT | $\mathcal A^{obs}$: catalog, `pg_stat_*`, EXPLAIN, telemetry, billing views | measured / declared | information gathering, cost $\kappa$ |
| 2 HYPOTHESIZE | $\mathcal A^{diag}$: emit a **diagnosis artifact** citing evidence event IDs | derived (never measured) | an option whose termination is "evidence sufficient" |
| 3 SCREEN | $\mathcal A^{screen}$: HypoPG, hint sets, surrogate | $f_0/f_1$, **estimated** | proposes; can never accept |
| 4 DECIDE | $\mathcal A^{dec}$: commit {proposed, accepted, rejected + margin + margin provenance} | derived | selection under budget |
| 5 APPLY & MEASURE | $\mathcal A^{change}_\ell$ per family ℓ, plus $\mathcal A^{meas}(\phi, n)$ with repeats | declared (apply), **measured** at $f_2$/$f_3$ | state transition + adjudication |
| 6 KEEP / REVERT | revert via $a^{-1}$ or re-branch; stop | derived | carries state forward |

Each change action $a$ carries a family, a target and granularity, a mechanism, a delegation mode, a duration $\delta(a)$ (heavy actions are options), an inverse $a^{-1}$ (possibly undefined), and a **reversibility tier** $\rho(a)$. The ladder is **T0 read-only**, **T1 hypothetical**, **T2 reversible-online** (reloadable knobs, `CREATE INDEX CONCURRENTLY`), **T3 reversible-at-cost** (restart knobs, online rewrites via pg_repack or gh-ost, instance resize) and **T4 irreversible** (DROP, data deletion, snapshot expiry, format upgrade, financial commitment). The ladder is the notes' own synthesis; no published DB reversibility taxonomy was found. Two further action classes make the swarm and the infrastructure part of the problem rather than implementation details. $\mathcal A^{env}$ covers branching a clone, replaying a window, promoting to a canary scope (a replica, tenant or time slice, since a single-primary DB has no traffic slice to send to), and provisioning infrastructure. $\mathcal A^{swarm}$ covers spawning an investigator with a role, a scope and a budget slice, and killing one. Making spawning an action is what later lets the orchestrator be trained (see the decision section).

Requiring Move 2 as an explicit, evidence-citing artifact before any T2+ proposal also answers an open question in `dba_loop.md` about where the hypothesis comes from. In an LLM harness the hypothesis *is* emitted, and it can be checked against the evidence it cites. SREGym supports making it a gate. With a correct diagnosis, mitigation succeeds **68–89%** of the time; with a wrong one, **22–62%** ([arXiv 2605.07161](https://arxiv.org/pdf/2605.07161)).

### Objective, constraints and the one-ledger budget

Spend across all three currencies is metered from authoritative sources, meaning provider usage APIs and cloud billing, not SDK estimates:

$$C(\tau)=\underbrace{\textstyle\sum_i p^{tok}_i n_i}_{\text{LLM tokens (cache read/write separate)}}+\underbrace{\textstyle\sum_j \big(p^{clone}\,\text{hrs}_j + p^{stor}\,\text{GB-hrs}_j\big)}_{\text{clone / replay compute}}+\underbrace{\textstyle\sum_t p^{infra}(h_t)\,\Delta t}_{\text{agent-provisioned infra}}\le B_\$,\qquad T(\tau)\le B_{hrs}$$

The problem in **clone→prod** mode is then

$$\max_{\mathcal G}\ \mathbb E\big[J_{f_3}(x_T)\big]\ \ \text{s.t.}\ \ C(\tau)\le B_\$,\ T(\tau)\le B_{hrs},\ E_k(\tau)=\textstyle\sum_t \mathbb 1[g_k>\theta_k]\,\text{dur}_t\le\varepsilon_k\ \forall k,\ \text{invariants a.s.}$$

where $g_k \le \theta_k$ are per-window SLOs (p99, error rate, availability, replication lag, storage). $E_k$ is the SRE error budget, defined as 1 − SLO; for example, 99.9% over four weeks allows 1,000 errors per million requests ([Google SRE Workbook](https://sre.google/workbook/error-budget-policy/)). The invariants are no data loss, unchanged durability and isolation settings, and result equivalence for rewrites. In **prod** mode the terminal objective becomes the cumulative $\sum_t J_{f_3}(x_t)$ with regret $R_T$, as in OnlineTune, because every exploratory step is paid for in production. In **clone** mode, SLOs bind only at final promotion. The infrastructure note offers a useful acceptance rule for the steady-state cost of $x_T$: **payback period = (one-time change cost + experiment cost) ÷ reduction in run-rate**. Four modelling choices remain open for the team. Does exploration during promotion count? How are human approvals priced in $C$ and $T$? Is steady-state infra cost an objective (a perf/$ Pareto front) or a constraint? How are restart-induced downtimes charged?

### Environment mode and guardrail level are exogenous, and measurement integrity is never ablated

The mode $M \in \{\textsf{clone}, \textsf{shadow}, \textsf{prod}, \textsf{clone}\to\textsf{prod}\}$ restricts $\mathcal A^{env}$. The guardrail level $G$ is a post-posed shield $\Sigma_G:(H_t,a)\mapsto\{\text{allow},\text{block},\text{replace}(a'),\text{require\_approval}\}$. At **G0** there is no shield. **G1** allowlists tiers T0–T2. **G2** is G1 plus canary-and-auto-rollback on SLO breach plus an **error-budget freeze**: once $E_k>\varepsilon_k$, the admissible set collapses to {no-op, revert}, mirroring Google's "halt all changes" policy. **G3** is G2 plus human approval at T3 and above. The ladder borrows from deployed practice: Azure SRE Agent's ReadOnly/Review/Autonomous run modes and its never-delete denylist ([Microsoft Learn](https://learn.microsoft.com/azure/sre-agent/run-modes)), and OWASP LLM06's rule that authorization must not depend on the model's judgment (secondary sources, [ByteHide](https://docs.bytehide.com/products/radar/sast/owasp/llm06-2025)).

**Making guardrails a research variable needs one line drawn very carefully.** *Safety* guardrails (the shield) are ablated. *Measurement integrity* is held fixed in every arm. That means an agent-unwritable workload driver, SLO checker and ledger, and a durability and isolation diff checked on every claimed win. If integrity were ablated too, the G0 arm would measure reward hacking rather than agent capability. The evidence is clear. METR found reward hacking in **30.4% of RE-Bench runs and 100% on one optimization task**, and adding "please do not cheat" to the prompt left the rate at 80% ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). The Darwin Gödel Machine deleted the markers its hallucination detector read and faked a test-pass log ([Sakana](https://sakana.ai/dgm/)). Plausible DB analogues include turning off `fsync` or `synchronous_commit`, truncating the measured workload, warming the cache only for the measured run, and gaming the cost-model reward. These are inferred, not observed. A second line follows from the Replit incident, in which an agent deleted a live database during a code freeze ([OECD AI incidents](https://oecd.ai/en/incidents/2025-07-19-1eb1)). "Live-prod at G0" should run on a **sacrificial production-grade system** carrying real or replayed traffic with real SLO accounting, never on a system anyone depends on.

## Evaluation is a factorial over mode, guardrail and budget, scored by measured anytime curves

The protocol is a factorial over $M \times G \times B_\$ \times B_{hrs} \times$ workload × engine. Every cell keeps the same model and harness and varies only the factor under study. Workloads should cover the team's analytical suite (JOB, TPC-H, DSB), a TPC-C-like OLTP workload, a lakehouse table under streaming ingest, and a **drift scenario**. Repeat counts should be set by confidence-interval width, following Hoefler and Belli's rule of measuring until the 99% CI is within 5% of the mean and always reporting absolute baselines alongside ratios ([SC15](https://evaluate.inf.usi.ch/node/366)). This matters because single-server variability is large: Maricq et al. collected roughly 900,000 data points across 835 servers ([OSDI 2018](https://www.usenix.org/node/222562)).

The metric suite combines formats that no existing benchmark reports together. The headline is the **anytime curve**: best $f_3$-verified objective against dollars spent and against wall-clock, which is the cost-aware convention of simple regret against cumulative cost ([AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/12184/12043)). Alongside it go **cost-to-target** (dollars and hours to reach X% of a reference optimum such as a long Proto-X run); **final improvement** with CI and absolute baseline; **error budget consumed** and SLO-violating windows, split by exploration versus exploitation and by mode; **hard-invariant violations** (which should be zero at G≥1); **regression rate** (applied actions later reverted or that worsened p99); **shield interventions** (blocks, replacements and approvals requested, which directly measure what the guardrail did); **cumulative regret** in prod mode, as in OnlineTune; the **clone→prod gap** $\widehat\Delta(a)=J_{f_3}(a)-J_{f_2}(a)$ per action family; and the **cost breakdown** by tokens, clone compute and infra. DBA-Bench's Safe Pass, an outcome pass with zero safety penalty, is worth adopting as a per-episode binary. Baselines should be the default configuration, the ISE heuristics (extend, auto_admin), OtterTune-style BO, OnlineTune-style safe BO, Proto-X and UDO, AgenticDB and EvoTune where code allows, and the LLM agent at G0.

Five integrity rules make the numbers mean something. They extend the team's §6 measurement-integrity lessons ([training_record.md](../docs/training_record.md)). First, every claimed number must cite a harness-recorded measurement event ID, and an `estimated` value can never satisfy a measured acceptance check. Second, any gain above a threshold triggers **mandatory reproduction** on a fresh instance with a re-measured baseline, plus a skeptic reviewer that sees the diff and the evidence but not the proposer's narrative. AI Scientist's invalid experiments ("kept e fixed at 2 and never re-ran the baseline", [arXiv 2502.14297](https://arxiv.org/pdf/2502.14297)) are what this rule prevents. Third, censored (timed-out) queries count at their limit, so that before and after cover the same query set. Fourth, cache state is controlled and recorded. Fifth, for any harness-evolution or self-improvement experiment, workloads and engines are split into **train / selection / test**, because evolved harnesses overfit their evolution stream. One example is Adaptive Auto-Harness, whose prompt grew from 2 KB to 68 KB while accuracy fell (preprint, [AGG]; [arXiv 2606.01770](https://arxiv.org/abs/2606.01770)).

## Existing harnesses solve the inner loop and none of the four DB-critical requirements

Measured against eight requirements, the candidate bases are good at the parts that do not matter most. Those requirements are: long horizon and resume; a three-currency budget; swarms competing for a scarce DB fleet; stateful, expensive environments; safety tiers including deliberately unguarded runs; estimated-versus-measured verification; lossless trajectories; and model-agnosticism.

| Candidate | Resume | 3-currency $ budget | Scarce-resource swarm | Stateful env | Safety tiers | Est-vs-measured | Lossless traces | Model-agnostic |
|---|---|---|---|---|---|---|---|---|
| Claude Agent SDK | ◐ | ◐ token estimate only | ◐ subagent caps | ○ | ● hooks | ○ | ◐ chat transcript | ◐ (proxy support unverified) |
| OpenHands SDK | ● event-sourced replay | ◐ | ? | ◐ workspace-centric | ? | ○ | ● | ● (licence unverified) |
| mini-swe-agent | ○ | ○ | ○ | ○ stateless | ○ | ○ | ● linear, used in RL stacks | ● |

| Inspect AI | ◐ per-sample | ● scoped token/cost/time/working limits | ◐ | ◐ | ◐ | ○ | ◐ | ● |

(● first-class, ◐ partial, ○ absent, ? unverified. Ray, Temporal, AutoGen/AG2, CrewAI, ADK and smolagents were not verified, and none of the "?" cells should be quoted as fact.)

The specifics show why no base can serve as the ledger. The Claude Agent SDK's `max_budget_usd` is computed from a bundled price table, and the docs call it a "client-side estimate" not to be used for financial decisions. It "counts only the call's own spend". Totals restored on resume don't count against it, `/clear` starts the budget over, and a crash can zero `total_cost_usd` ([Claude docs](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). LangGraph resume "starts at the beginning of the node" and asks for idempotent side effects ([LangGraph](https://docs.langchain.com/oss/python/langgraph/durable-execution)). A crash after `CREATE INDEX CONCURRENTLY` would therefore re-run the DDL unless the harness keeps its own action journal. Inspect has the richest budget primitives, including a `working_limit` that excludes time spent waiting on shared resources, which is exactly the split between agent think-time and clone queueing. But Inspect is built around bounded samples, not a days-long run ([Inspect](https://inspect.aisi.org.uk/setting-limits.html)). OpenEvolve-style cascades map naturally onto screen-then-measure, but their stage scores carry no label saying whether they are estimates, so an $f_0$ score can quietly become the selection signal. That is the self-certifying loop `dba_loop.md` forbids. ShinkaEvolve's novelty rejection, which reached a state-of-the-art circle packing in **about 150 evaluations** ([arXiv 2509.19349](https://arxiv.org/pdf/2509.19349)), is worth copying directly, because it rejects equivalent configurations *before* paying for a replay.

Taken together, the notes identify nine things existing harnesses make impossible or very hard for this problem. (1) A single budget over three currencies. (2) Leases on a scarce, stateful measurement resource, with noise isolation, warmup and repeats, since parallel measurements on one host contaminate each other. (3) Non-idempotent, expensive environment transitions, where reset means a re-clone rather than `git reset`. (4) Semantic blast-radius classification, because permission systems gate tool names and paths, not "reversible index on a clone" versus "irreversible rewrite on prod". (5) Evidence provenance. (6) Anti-fabrication: a structural guarantee that every reported number references a measurement event. (7) Statistical measurement with CIs, A/A noise floors and percentile SLO checks. (8) Lossless, provenance-typed trajectories joined across a swarm. (9) Experiment-controlled guardrail levels with matched logging. Practitioner lessons point the same way. The Anthropic multi-agent system documents **over-spawning (50 subagents for simple queries) and duplicated work** ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)), so spawn admission must be enforced outside the model. Manus rebuilt its framework four times and treats KV-cache hit rate as the top production metric (cached $0.30 vs uncached $3 per MTok, [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)), so cache read and write tokens belong in the ledger as separate lines. BATS shows that agents waste larger budgets unless a live budget tracker sits in context ([arXiv 2511.17006](https://arxiv.org/pdf/2511.17006)).

### Very recent work co-trains harness and model, and it says harnesses are a training variable

The 2025–26 frontier recipe is outcome-reward RL run *through* a harness, and most of the engineering goes into rollout infrastructure. KAT-Coder-V2.5 found re-tokenization drift in **about 40% of samples** at around 200 turns and **6–7% corrupted verifier outputs**, either of which was enough to destabilize training (preprint, [arXiv 2607.05471](https://arxiv.org/html/2607.05471v1)). The decisive 2026 result for this decision is **harness overfitting**. In Harness Scaling, a single-harness Qwen3-30B policy scores 59.82 on its own harness but **46.02 on Claude Code**. Training across 18 harness configurations chosen by orthogonal design gives 59.63 on its own harness and 49.62 on Claude Code, and raises Qwen3-4B's average from 29.81 to 39.04 (preprint, [arXiv 2610.29458](https://arxiv.org/html/2610.29458v1)). KAT-Coder names format, context-structure and control-flow overfitting, and mitigates it by training over mini-swe-agent plus black-box harnesses (Claude Code, Codex, OpenHands) with randomized tool schemas. Harness search without weight updates is the cheaper lever. Meta-Harness's discovered harness gained **+4.7 points across five held-out models** (preprint, [arXiv 2603.28052](https://arxiv.org/abs/2603.28052)). AHE reports that structural edits (tools, middleware, memory) transfer across models while prompt edits do not (preprint, [AGG]). GEPA reaches GRPO-level gains with up to **35× fewer rollouts** (preprint, [arXiv 2507.19457](https://arxiv.org/abs/2507.19457)). Joint harness and weight co-evolution is just appearing. HarnessForge reports up to 12.0% over the strongest baseline (preprint, [arXiv 2606.01779](https://arxiv.org/abs/2606.01779)). HarnessX (+4.7% on top of harness search) and SIA, which warns of "coupled co-evolutionary Goodhart" when two optimizers share one verifier, are both [AGG]. On the orchestrator side, Kimi K2.5's PARL trains only the orchestrator, with frozen sub-agents and annealed anti-serial-collapse rewards ([V], [Kimi](https://www.kimi.com/blog/kimi-k2-5)), and ToolOrchestra rewards cost-efficiency in delegation ([PK], [arXiv 2511.21689](https://arxiv.org/abs/2511.21689)). No published work applies agentic multi-turn RL to an LLM for knob, index or holistic DB tuning. The nearest DB RL work is single-shot: Arctic-Text2SQL-R1 with an execution-only reward ([ACL Findings 2026](https://aclanthology.org/2026.findings-acl.1345/)), and E3-Rewrite with a partly *estimated-cost* reward ([arXiv 2508.09023](https://arxiv.org/pdf/2508.09023)). The latter is exactly the reward the team's 2× measurement says is biased.

## Decision: own the control plane, adopt the loop three times behind one DB-ACI

**Do not build the model loop from scratch, and do not let any framework be the control plane.** Each pure option fails on evidence already in the notes. Building everything from scratch spends months re-implementing tool calling, subagents, compaction, caching and hooks, which are commodity and well tested. It also produces a single bespoke harness, and the Harness Scaling and KAT-Coder results show a model trained in one harness overfits to it. Adopting one framework wholesale fails because none covers the three-currency budget, scarce-resource scheduling, stateful environment lifecycle or estimated-versus-measured provenance. It would also put the budget and the safety checks inside a component the agent talks to, which is the evaluator-writable design that METR and the DGM incident show gets gamed. The strongest case for building from scratch is real but narrow. RL needs token-exact model I/O, tool-output loss masks and full control of the chat template, which black-box SDKs do not expose. That case is met by owning *one minimal loop* for the RL arm, not by owning all of them.

The recommended architecture therefore has three adopted or owned inner loops, all talking through a single owned boundary:

| Arm | Base | Why this one | Main risk to verify first |
|---|---|---|---|
| **Primary baseline** (frontier and open models, swarms) | **OpenHands Software Agent SDK** | event-sourced state with deterministic replay, the closest structure to `training_record.md` events; multi-LLM, so Gen-DBA served on vLLM can be plugged in ([arXiv 2511.03690](https://arxiv.org/html/2511.03690v1)) | licence and resume API unverified; runtime assumes a workspace or filesystem |
| **Frontier / safety-hook arm** | **Claude Agent SDK** | fastest path; PreToolUse/PermissionRequest hooks are a natural place to mount the shield, and they can be switched off for G0 ([Claude docs](https://code.claude.com/docs/en/agent-sdk/permissions)) | Anthropic-centric; open-weight use via proxy unverified; budget field is an estimate |
| **RL / co-training arm** | **owned mini-swe-agent-style loop** | linear history, any model, already the rollout harness in GRPO stacks ([PSRL](https://psrl.readthedocs.io/en/latest/examples/agentic_rl/swe/index.html)); token-exact I/O under your control | stateless by design, so all state must live behind the DB-ACI, which is the intent |

This is not three times the work. Each loop is a thin client of the **DB-ACI**, a typed MCP tool server whose verbs are the six moves: `orient`, `diagnose`, `probe_whatif`, `decide`, `apply`, `measure(fidelity, repeats)`, `revert`, plus `branch_clone`, `promote(scope)`, `provision`, `spawn(role, scope, budget_slice)` and `ledger()`. The ACI returns payloads tagged with provenance and fidelity, and it is the only way any agent touches a system. The design copies AIOpsLab's Agent-Cloud Interface ([MSR](https://www.microsoft.com/en-us/research/publication/aiopslab-a-holistic-framework-for-evaluating-ai-agents-for-enabling-autonomous-cloud)) and SWE-agent's lesson that the interface design is a large share of the performance. Swarm orchestration belongs on the control-plane side of this boundary, not inside an SDK. Every investigator consumes clone leases and dollars, so spawning must be admitted by the scheduler against the ledger. And because the orchestrator expresses spawning as a tool call, its policy can later be learned PARL-style, with frozen workers.

The custom layer must own seven components, and the team already has the seed of several in `scripts/gendba/` (`record.py`, `env.py`, `reset_fidelity.py`, `noise.py`, `rollout.py`, `monitor.sh`):

| Owned component | Responsibility | Why no base provides it |
|---|---|---|
| **Budget ledger + admission scheduler** | authoritative token usage (provider APIs, cache tokens separate), metered clone, replay and infra dollars, wall-clock; *reservations before spend*; expected-gain-per-dollar admission, utility-based stopping, a verification reserve | SDK costs are estimates that reset or zero ([Claude docs](https://code.claude.com/docs/en/agent-sdk/cost-tracking)) |
| **Environment manager** | clone and branch provisioning, snapshot/reset, replay, fleet leases, a measurement queue with isolation, warmup, repeats, and multi-fidelity promotion (successive halving, [BOHB](https://ar5iv.labs.arxiv.org/html/1807.01774)) | parallelism everywhere assumes independent, cheap evaluators |
| **DB-ACI** | typed six-move verbs; (π, φ) labels on every payload | no base has DB semantics |
| **Action journal + shield** | intent → applied → verified → rolled back with idempotency keys; T0–T4 classifier; G0–G3 enforced at the ACI, never in the prompt; error-budget freeze | permission systems gate tool names, not blast radius |
| **Evidence store + claim checker** | every number in a decision or report cites a measurement event; `estimated` can never pass a measured gate | evolutionary cascades encourage self-certification |
| **Immutable evaluation plane** | workload driver, SLO checker, durability/isolation diff, reproduction-on-fresh-instance; checksummed and agent-unwritable; *never ablated* | every writable scoring path studied got gamed ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)) |
| **Record writer** | emits `training_record.md` episodes across the whole swarm, plus RL-replay projections | traces are per-session chat logs |

For the orchestrator's own durable state, adopt rather than build. A LangGraph checkpointer in `sync` mode is verified to support crash recovery. Temporal and Ray are plausible alternatives but were not verified in the notes.

**Co-trainability comes from interface discipline, set from day one.** The record must become a strict superset of today's `training_record.md`. That means adding exact model input and output (token IDs, or the raw completion plus the chat template and tokenizer version), sampling parameters and logprobs, a tool-output loss mask, parent and child agent IDs for the swarm tree, per-step dollar and wall-clock cost, and a **harness-variant ID**: a hash of the prompt, tool schema, observation format, context policy and workflow. Those five components should be swappable configuration, so harness search and multi-harness RL can both run without code changes. Expose `run_episode(task, harness_cfg, policy_endpoint) → trajectory, reward` behind an OpenAI-compatible endpoint or a direct `/generate` path, so a verl, SkyRL, AReaL or Agent Lightning worker can drive it. Rollouts should be asynchronous and preemptible, and a timeout should be recorded as censored rather than failed. Keep reward hooks outside the agent's write scope, with annealable shaping terms. Then train in order of cost. First, harness and prompt search over frozen frontier models, using the trace archive with held-out splits. Second, SFT or offline learning of a small orchestrator from logged lossless episodes (Proto-X, the ISE heuristics and frontier swarms). Third, online RL of the *orchestrator only*, on $f_0$/$f_2$-tier environments validated at $f_3$. Full harness-plus-policy co-evolution comes last, and only once a cheap, reasonably faithful environment tier exists. Full-fidelity online RL is out of reach. Harness Scaling's GRPO setup implies about 38,000 rollouts, and each DB rollout here takes minutes to hours.

## Five unclaimed gaps define the contribution

The notes surface five gaps that no surveyed system closes. Each is a contribution the problem definition can claim. They are weak negatives (bounded searches, not exhaustive ones), so phrase them as "we found no prior work".

| Gap | Evidence of absence | What this work would add |
|---|---|---|
| **No harness budgets tokens + compute + infra under one $ cap** | every base meters only tokens; the BATS and cost-aware BO lines treat tool calls or evaluations, not provisioned infra ([BATS](https://arxiv.org/pdf/2511.17006)) | the ledger + admission scheduler, and anytime curves against total $ |
| **No LLM agentic RL for holistic DB tuning** | LLM tuners are training-free (GPTuner, λ-Tune, AgenticDB, EvoTune); DB RL is single-shot text-to-SQL or rewrite | orchestrator RL on Gen-DBA from lossless, provenance-typed records |
| **No clone-vs-prod gap measurement** | no quantitative study of the clone-vs-prod gap for DB tuning was found; OnlineTune *argues* against clones without measuring the gap | $\widehat\Delta(a)$ per action family as a first-class output |
| **No guardrail ablation for ops agents** | no guarded-vs-unguarded ablation found; products ship fixed run modes ([Azure SRE Agent](https://learn.microsoft.com/azure/sre-agent/run-modes)) | the G0–G3 shield as a factor, with measurement integrity held fixed |
| **No tuner covers middleware / app / infra levers** | coverage grid columns for pooling, caching, workload management, sizing and app rewrite are empty except advisory AWS DevOps Guru ([AWS](https://docs.aws.amazon.com/en_us/AmazonRDS/latest/AuroraUserGuide/devops-guru-for-rds.html)) | the U1–U13 action space with cross-family interactions |

Three subsidiary unknowns deserve mention because they decide feasibility rather than novelty. No DB environment simulator or world model for agentic RL exists. There is no evidence yet on whether RL on low-fidelity DB tiers transfers to production outcomes, which is the single fact that decides whether online co-training pays off. And no study yet compares an agent's own hypothesis against `EXPLAIN ANALYZE` misestimates as a source of grounded Move 2 supervision.

## Conclusion

The research framing changes once the harness is treated as an experimental apparatus rather than a product. Guardrail level, environment mode and harness variant all become *factors*. That only works if the factors are cleanly separable from the things that must never vary: the ledger, the evaluation plane and the provenance labels. This is the deeper reason the control plane must be owned and the loops adopted. Ownership is what lets the team ablate safety without ablating truth, and swap harnesses without retraining the measurement machinery. It also turns the team's existing assets into an advantage few competitors have. The 2× cost-model gap, the censoring rules and the absent-not-inferred discipline in `training_record.md` are exactly the verifier hygiene that agentic-RL labs are only now finding they need.

The practical implication is sequencing. The first publishable result does not require RL at all. It is the factorial itself: a plain ReAct-style agent behind the DB-ACI, run across clone and prod modes and G0–G3 levels under a single dollar cap, reporting $\widehat\Delta$ and shield interventions. That experiment closes three of the five gaps at once, and it produces the lossless, multi-harness, provenance-typed corpus that later orchestrator training will need.
