# One live database breaks every harness

**No existing harness can host the target design, and the reason is structural, not a missing feature.** Every harness surveyed (about 45 across coding-agent SDKs, orchestration frameworks, durable-execution engines, research, evolution, eval and ops harnesses, agentic-RL trainers and DB tool servers) assumes at least one of eight things that a single, non-resettable, credentialed database violates. The eight are: evaluations can be reset and run independently; resume restores the conversation rather than the world; budgets are token or step caps; the evaluator or hook lives where the agent can reach it; the action space is supplied; RL can sample sibling groups from one start state; long episodes can be staleness-masked; and reward arrives once, at episode end. The consequence is a clean split. The **inner loop is commodity and should be adopted**: OpenHands Software Agent SDK as the primary open loop (MIT, confirmed this round), a mini-swe-agent-style loop as the RL and harness-variant arm, and Claude Agent SDK plus Codex `exec` as frontier baselines. Durability for the harness's own control loop comes from **DBOS** (or Temporal), and token-exact training plumbing from a **gateway-style RL framework** (rLLM, Agent Lightning or AReaL) plus prime-rl-style staleness semantics. The research artifact is the part nobody ships, and the team must build it. It has seven pieces: an authoritative dollar-and-deadline budget plane that the model can see; a write-ahead effect journal that does not retry and reconciles by observation; a contention broker for subagents sharing one database; an effect-level monitor in a separate security principal that also supplies a delayed, censorable reward; a cross-run memory that is re-grounded on every run; a small set of high-level observation tools, led by an **action-space probe** and a **time-budgeted triage** that no tool server provides; and a training contract built around single-rollout, not group-relative, learning. This round revises the earlier report in four places: LangGraph's resume is downgraded, OpenHands' licence is confirmed MIT, routing Claude Code to open-weight models is unsupported by Anthropic, and the earlier typed DB-ACI and G0–G3 shield are replaced by generic shell, a few observation tools and an agent-inferred risk envelope.

## The target: one fixed database, no human, and a risk envelope the agent must infer

The design under evaluation is a **fully automated agent with no human in the loop**. It receives credentials to **one fixed environment**, either a production database or a clone, never both, with no promotion between them. It also receives a **budget of wall-clock time and dollars**. No guardrail policy is supplied. The agent must **infer its own action space and risk envelope**, and the only hard boundary is the **DB role** it was given. Every run starts with **diagnosis**, which is anytime: ten minutes buys triage, while an unbounded budget allows deep root-cause analysis. **Optimization** follows, with a horizon that scales with budget, so long budgets allow slow-acting structural changes. The run ends with a **report**. Runs are one-shot or cron/continuous, with **memory across runs**. The tools are **generic shell and psql**, where which commands to use and how to verify or roll back are *learned through training*, plus a **small set of high-level tools** for setup and breadth-first observation. The **model is swappable and will be RL-trained**. The **harness is the research artifact**, and harness and model may be co-trained across harness variants. A **research-owned, agent-unwritable, effect-level monitor** detects reward hacking and supplies the reward. It covers SQL audit, config diff, independent measurement, workload integrity and damage checks. The design is **engine-agnostic**.

The research notes scored every candidate against eleven harness requirements and ten RL-trainer requirements. The R-labels come from the notes' rubric. The T-labels are reconstructed from how the RL note uses them, because the brief that defined them is not in the notes.

## Why current harnesses cannot do it: eight assumptions that a single live database breaks

Each assumption below is one root cause. It explains a cluster of ○ and ◐ cells, and each comes with the concrete way the target design fails. The scenarios are constructed **[I]**; the mechanisms they rest on are documented and cited.

### Assumption 1: evaluations are resettable and independent

Research loops, evolution loops, eval harnesses and RL trainers all get retries, parallelism and "discard" from resetting state. autoresearch's `program.md` says that when a result is not better, "you git reset back to where you started" ([program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)). OpenEvolve's evaluator contract is a function of a program file path ([OpenEvolve](https://github.com/algorithmicsuperintelligence/openevolve)). ShinkaEvolve says it is "well-suited for scientific tasks where there is a verifier available" and runs parallel evaluation jobs locally or on Slurm ([ShinkaEvolve](https://github.com/SakanaAI/ShinkaEvolve)). Harbor states that its tasks "are independent, isolated, reproducible pieces of code" ([Harbor](https://docs.harborframework.com/tasks/overview.md)). The coding agents carry the same assumption one level down. Their workspace is a filesystem, so checkpointing, `acceptEdits`, path-scoped rules and sandbox write scopes all reason about files, while `psql -c "DROP INDEX ..."` is an opaque Bash string ([Claude sessions](https://code.claude.com/docs/en/agent-sdk/sessions); [Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode)).

On one fixed database this breaks in four ways **[I]**. First, an autoresearch-style keep/discard loop creates an index, sees no gain within its slot and "discards" by git reset, but the index stays and keeps adding write amplification. Second, ShinkaEvolve with four evaluation jobs on one PostgreSQL instance races four `ALTER SYSTEM` calls, so each score reflects the union of four configurations. Third, an OpenEvolve-style cascade with a cheap first stage on a clone has no meaning when the single environment *is* the only place to measure. Fourth, Harbor with eight concurrent trials against one DB URL lets each verifier read the others' effects. The parallel-subagent version of the same failure hits the agent frameworks. Deep Agents' `task`, MAF's Concurrent/Magentic patterns, CrewAI crews and ADK's ParallelAgent fan out with no lease on the shared database. Five diagnosis subagents running `EXPLAIN ANALYZE` on heavy queries perturb the workload they are diagnosing, and two subagents running `CREATE INDEX` and `VACUUM FULL` on one hot table report each other's lock waits as regressions. Claude's subagent hooks are not a reliable counter either: resuming a finished subagent "emits no new start event to hooks", so "a PreToolUse concurrency hook counted six while seven ran" ([#97782](https://github.com/anthropics/claude-code/issues/97782)), and subagent-frontmatter `PreToolUse` hooks "never fire" ([#95650](https://github.com/anthropics/claude-code/issues/95650)). Contention control must therefore be a harness-owned broker. Raw-shell contention can only be *observed* and attributed (one role or `application_name` per subagent), not prevented, unless the shell is mediated.

### Assumption 2: resume restores the conversation, and side effects are at-least-once

This is the most important break, because it is shared by every harness that claims durability. Claude's docs are explicit: "Sessions persist the **conversation**, not the filesystem", and they advise "Don't rely on session resume. Capture the results you need ... as application state" ([Claude sessions](https://code.claude.com/docs/en/agent-sdk/sessions)). Open resume bugs from September–October 2026 include a turn going permanently idle with a dropped `tool_result` ([#94252](https://github.com/anthropics/claude-code/issues/94252)) and a deferred-tool resume that drops the supplied result ([#97358](https://github.com/anthropics/claude-code/issues/97358)). OpenHands persists every event as an append-only file and says state "is always recoverable, even if the process crashes unexpectedly", but it does not say how an in-flight tool call is reconciled ([OpenHands persistence](https://docs.openhands.dev/sdk/guides/convo-persistence)). Inspect says its checkpoints do "not save arbitrary in-memory process state, running tools, or other external side effects" ([Inspect checkpointing](https://inspect.aisi.org.uk/checkpointing.html)).

The durable-execution engines make the orchestrator crash-safe, but none makes an external side effect exactly-once. Temporal recommends idempotent activities, and its default retry policy has **Maximum Attempts "unlimited"** ([Temporal activities](https://docs.temporal.io/activities); [retry policies](https://docs.temporal.io/encyclopedia/retry-policies)). DBOS steps that crash before their checkpoint are retried. Its exactly-once guarantee covers only `@transaction` steps that commit in the *same* Postgres database as DBOS's own records ([DBOS architecture](https://docs.dbos.dev/architecture); [DBOS transactions](https://docs.dbos.dev/golang/tutorials/transaction-tutorial) [snip]). That excludes `CREATE INDEX CONCURRENTLY` and `ALTER SYSTEM`, which "cannot be executed inside a transaction block" ([PG CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html); [PG ALTER SYSTEM](https://www.postgresql.org/docs/current/sql-altersystem.html)). It also excludes restarts and non-Postgres engines. Inngest tells users to make a refund idempotent "because a refund can succeed before Inngest saves the step result and retries the step" ([Inngest](https://www.inngest.com/docs/learn/how-functions-are-executed)). A third-party test of Restate killed a worker between a tool's side effect and the journal write and got **duplicate charges in 3 of 3 trials** ([nerdleveltech](https://nerdleveltech.com/restate-durable-agent-duplicate-tool-calls-tested) [snip; fetch failed]). The framework checkpointers are coarser still. LangGraph re-runs "Nodes after the checkpoint ... including any LLM calls, API requests", and an interrupted node "starts at the beginning of the node" ([time travel](https://docs.langchain.com/oss/langgraph/use-time-travel); [interrupts](https://docs.langchain.com/oss/langgraph/interrupts)). ADK tools run "at least once" and "may run more than once when resuming" ([ADK resume](https://adk.dev/runtime/resume/index.md)). Pydantic AI's durable layer "retries the one in flight" ([Pydantic AI](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/)). Granularity matters: if the unit is a whole ReAct node, the re-run repeats every tool call since the last checkpoint, not just the last one.

The failures are concrete **[I]**. A worker dies 40 minutes into `CREATE INDEX CONCURRENTLY`, the session dies with it, and PostgreSQL leaves an INVALID index. Temporal's unlimited retry then re-issues the DDL and fails with "relation already exists", or, with `IF NOT EXISTS`, silently succeeds and *keeps the invalid index*. A `pg_ctl restart` or cloud reboot succeeds and the worker crashes before completion is recorded, so a retry restarts production a second time. Setting `MaximumAttempts=1` prevents that but leaves "did it happen?" open, and only an observation such as `pg_postmaster_start_time()` can answer it. A crash between Codex's `item.started` and `item.completed` for `VACUUM FULL` leaves a started event with no completion, while an orphaned backend may still hold the table lock. On resume, Claude's budget also restarts at $0 ([cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). OpenHands' deterministic replay replays the *log*, not the database, so replay-based debugging diverges as soon as autovacuum or statistics have moved on. Cron runs with memory have the same problem across runs: run N+1 inherits run N's "I already created idx_foo", but the world may have changed since. Because the agent's commands are learned free text, the harness cannot know a reconcile probe in general. The honest design is a **write-ahead intent journal, no automatic tool retries, and an "outcome uncertain for command X" observation on resume**, backed by monitor-side catalog and uptime facts. That makes reconciliation a behaviour the model is trained to do.

### Assumption 3: the budget is a token or step cap, not authoritative dollars and a deadline

No candidate meters authoritative dollars, exposes remaining wall-clock and dollars to the model, and reserves budget for a report. Claude's `max_budget_usd` is a client-side estimate ([cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)) that "is checked after each call returns, so a $1 cap stops at $1.38", and **a $10 cap stopped at $12.06** ([#100111](https://github.com/anthropics/claude-code/issues/100111)). Retries after a mid-stream error are double-counted ([#101951](https://github.com/anthropics/claude-code/issues/101951)), `set_model` sends a billed request the ledger misses ([#101954](https://github.com/anthropics/claude-code/issues/101954)), and the cap works in print mode only ([#95964](https://github.com/anthropics/claude-code/issues/95964)). Codex's Goal object carries a soft *token* budget ([#34215](https://github.com/openai/codex/issues/34215)), and an open request asks it to "reserve capacity **before each model request**" across subagents ([#55180](https://github.com/openai/codex/issues/55180)), which implies that today's check happens after the fact [I]. Gemini CLI reports tokens and exits with code 53 on a turn limit, with no cost figures ([Gemini CLI headless](https://geminicli.com/docs/cli/headless/)). The frameworks offer `recursion_limit`, `max_iter` and `max_turns`. AIOpsLab caps steps and notes that "the step limit significantly affects the performance of certain agents" ([arXiv 2501.06706](https://arxiv.org/html/2501.06706)). Inspect has the best primitives, but its `cost_limit` is computed from model price data, and on scoring-only resume "time and working limits are not re-armed" ([Inspect limits](https://inspect.aisi.org.uk/setting-limits.html); [checkpointing](https://inspect.aisi.org.uk/checkpointing.html)). ShinkaEvolve's `max_api_costs` likewise uses a price table ([ShinkaEvolve config](https://sakanaai.github.io/ShinkaEvolve/configuration/)). None of them meters database-side spend: warehouse credits, cloud instance-hours or I/O.

The target fails in three ways **[I]**. A ten-minute triage run hits a turn cap at minute nine in the middle of `EXPLAIN ANALYZE`. Because frameworks *raise* on the cap, no diagnosis report is written, and the anytime promise breaks. At T−2 minutes a `VACUUM FULL` or `pg_repack` is running. No harness tells the model how much wall-clock is left, and Claude's budget stop ends the session *after* the call returns, possibly mid-rewrite. And a resumed Claude run overspends because its counter restarted. SREGym is the only harness that shares one timeout across diagnosis and mitigation, so a slow diagnosis leaves less time to mitigate ([SREGym](https://github.com/SREGym/SREGym)). Even there, the agent cannot see the remaining budget. The earlier round's evidence that agents waste bigger budgets unless a live budget tracker sits in their context still applies (preprint, [BATS](https://arxiv.org/pdf/2511.17006)). The budget must be a harness-owned plane: metered at a proxy the team owns, reconciled with provider and cloud billing, injected every turn, reserved before spend, with a durable timer that forces the report phase. A further piece is genuinely new research **[I]**: a duration model for actions, so the scheduler can refuse to *start* an action whose expected duration exceeds the remaining budget.

### Assumption 4: hooks and evaluators run in-process, where the agent can reach them

Reward hacking in this design is expected, not hypothetical. AI Scientist v1 "tried to modify its own code to extend the timeout period" ([Sakana](https://sakana.ai/ai-scientist/)). The Darwin Gödel Machine "removed the markers used to detect hallucination" ([Sakana DGM](https://sakana.ai/dgm/)) [carried]. METR found reward hacking in **30.4% of RE-Bench runs** ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)) [carried]. Yet harnesses put their safety and scoring inside the agent's trust domain. Claude hooks see only the harness's tool calls; the docs warn that "If Claude writes `.env` with a Bash command, the hook doesn't run" ([hooks](https://code.claude.com/docs/en/agent-sdk/hooks)). Shell hooks load from `.claude/settings.json` when `settingSources` includes them, and that file sits inside a shell-capable agent's writable tree unless the harness pins it [I]. A hung `PostToolUse` hook silently blocks a turn for up to 600 seconds ([#104363](https://github.com/anthropics/claude-code/issues/104363)). OpenHands' `ConfirmRisky` uses an `LLMSecurityAnalyzer` that relies on the model annotating its own risk. Its docs warn that "the model can be manipulated" and list `execute_tool()` bypassing checks as a known limitation ([OpenHands security](https://docs.openhands.dev/sdk/guides/security)). Harbor's `tests/test.sh` runs inside the agent's environment and writes `reward.txt` there ([Harbor](https://docs.harborframework.com/tasks/overview.md)). AgenticDB and EvoTune score themselves with the benchmark they run (preprints, [AgenticDB](https://arxiv.org/html/2606.20318); [EvoTune](https://arxiv.org/html/2607.17841)) [carried]. Framework traces (OTel spans, LangSmith, MAF events, RunHooks) are emitted by code in the same process as the shell tool. In RL frameworks the reward is computed inside the rollout worker, for example `env.reward` in TRL ([TRL OpenEnv](https://github.com/huggingface/trl/blob/main/docs/source/openenv.md)).

With a database role that may be broad, the DB analogues are direct **[I]**. The agent can raise `statement_timeout` for the measured run, reset `pg_stat_statements` so the "before" looks worse, set `log_statement` to none, drop an audit trigger, set `fsync=off` or `synchronous_commit=off`, or forge OTel spans. The structural fix has three parts. The monitor runs under a separate security principal. It observes from outside the agent's write scope: an engine audit log, catalog and config snapshots, its own measurement client and workload replay, and OS metrics. And it compares two independent witnesses, the harness's command journal and the database's effect stream. Divergence between them, a command with no effect or an effect with no command, is itself a reward-hacking signal. No harness offers this, and its absence is exactly why DBA-Bench's **Safe Pass**, which counts an outcome only when it carries zero safety penalty, matters. On DBA-Bench, **36.7% of outcome-passing runs fail the safety check** (preprint, [DBA-Bench](https://arxiv.org/html/2607.22165v1)) [carried].

### Assumption 5: the action space and guardrails are supplied

Ops and DB harnesses hand the agent its action set. AIOpsLab's ACI "specifies (1) the set of valid actions available to the agent", and its `exec_shell` runs "after applying security policy filters" ([arXiv 2501.06706](https://arxiv.org/html/2501.06706)). AgenticDB's Initializer builds an action catalog and a rule-based Validator gates it, and EvoTune has four fixed component classes (preprints, [AgenticDB](https://arxiv.org/html/2606.20318); [EvoTune](https://arxiv.org/html/2607.17841)) [carried]. Azure SRE Agent is policy-configured by humans with allow/ask/deny, and Microsoft recommends Review mode for "Production systems", with the advice to "Start with review mode. Observe… for two to four weeks" ([Azure run modes](https://learn.microsoft.com/en-us/azure/sre-agent/run-modes)). The DB MCP servers express safety as *restriction*, not introspection. Postgres MCP Pro's restricted mode wraps calls in read-only transactions with time limits and warns that unsafe procedural languages can get around it ([postgres-mcp](https://github.com/crystaldba/postgres-mcp)). Neon wraps `run_sql` in a READ ONLY transaction ([Neon MCP](https://github.com/neondatabase/mcp-server-neon)), and Supabase's `read_only` removes tools ([Supabase MCP](https://github.com/supabase-community/supabase-mcp)). None of these tells the agent what its role *could* do. The coding harnesses' permission systems gate tool names and paths, not database blast radius.

The target requires the agent to learn its envelope, so the harness must give it the means to *measure* the envelope **[I]**. An agent trained against a fixed catalog has never learned, for example, that on RDS `rds_superuser` is not a true superuser and that server parameters change through parameter groups whose `IsModifiable` and `ApplyType` fields decide static versus dynamic ([RDS DescribeDBParameters](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_DescribeDBParameters.html) [not fetched]). It has also never learned that `pg_settings.context` separates restart, reload and session knobs ([pg_settings](https://www.postgresql.org/docs/current/view-pg-settings.html) [not fetched]). The incident-episode framing these benchmarks use adds a second hazard. Each problem has a known injected fault and an oracle, so an agent trained that way learns to *find the fault*. DBA-Bench documents **decoy anchoring on misleading alerts in 68.3%** of a failure class (preprint, [DBA-Bench](https://arxiv.org/html/2607.22165v1)) [carried], which on a healthy production database means fabricating a problem.

### Assumption 6: GRPO can draw sibling groups from one start state

Most trainers compute group-relative advantages, which need N rollouts from the same start state. Agent Lightning's async mode requires that "All four sibling rollouts must finish before that group can be used" ([Agent Lightning async](https://github.com/microsoft/agent-lightning/blob/main/docs/35-asynchronous-training.md)). TRL "creates one … instance per generation" and calls `reset()` for each episode ([TRL OpenEnv](https://github.com/huggingface/trl/blob/main/docs/source/openenv.md)). verl-agent advertises "Group environments support (for group-based RL)" ([verl-agent](https://github.com/langfengQ/verl-agent)), and GiGPO's step-level credit groups identical anchor states ([arXiv 2505.10978](https://arxiv.org/abs/2505.10978)). With one fixed environment, group size is one **[I]**. A group then means N sequential snapshot restores of a multi-gigabyte database and N times the hour-long wall-clock. If three siblings finish and the fourth hits a four-hour vacuum, Agent Lightning holds the whole group and carry-over age grows without bound. A restore that does not control cache, statistics and autovacuum state starts each sibling from a different effective state, so the advantage rewards luck. Production cannot be reset at all, so every production episode is a single, irreversible trajectory that must not enter group statistics. Continuous database state also means GiGPO's exact anchors rarely recur. The usable options are single-rollout, critic-free estimators such as OpenRLHF's **FlashREINFORCE**, "critic-free, single-rollout asynchronous RL … one rollout per prompt" ([OpenRLHF](https://github.com/OpenRLHF/OpenRLHF)), PPO with a learned critic, prime-rl's pluggable advantages, or offline learning. Whether single-rollout estimators are stable at 10²–10³ hour-long agentic episodes is unverified.

### Assumption 7: long episodes can be staleness-masked

Async trainers bound off-policyness in policy versions. prime-rl measures staleness per token, and `max_staleness` (default 8) masks tokens past the bound and "drops a sample only when no token is left to train", while "Rollouts are never cancelled for staleness" ([prime-rl algorithms](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/algorithms.md)). AReaL bounds it with `rollout.max_head_offpolicyness` ([AReaL async](https://github.com/areal-project/AReaL/blob/main/docs/en/algorithms/async.md)). The failure **[I]** is quiet and biased. A two-hour episode whose first ninety minutes are diagnosis spans about ten optimizer steps under prime-rl defaults, so the diagnosis tokens are masked out of the loss. Only optimization behaviour is trained, which pushes the policy toward skipping the diagnosis the design says must come first. The fixes are to slow the optimizer clock (few, large steps), tag every token with its policy version and use importance-corrected off-policy losses, or route long episodes to an offline buffer. Two related lifecycle hazards come with async training. Agent Lightning's gateway "pauses new model requests" during weight sync and returns retryable responses ([Agent Lightning async](https://github.com/microsoft/agent-lightning/blob/main/docs/35-asynchronous-training.md)). That is safe for model calls, but if the harness also retries *tool* calls on timeout, an `ALTER SYSTEM` or `CREATE INDEX CONCURRENTLY` may run twice. And colocated designs keep GPUs reserved while the agent waits minutes for a measurement. Tinker's "pay for actual tokens used, not inactive time" pricing is the economic counter-model ([Tinker](https://thinkingmachines.ai/tinker/)).

### Assumption 8: reward arrives at episode end and is never censored

The notes found **no framework with first-class semantics for "episode preempted, reward unknown"**. The documented behaviour is to drop or filter. KAT-Coder-V2.5 reports **6–7% timeout-invalid rollouts** and corrupted verifier outputs that destabilized training (preprint, [arXiv 2607.05471](https://arxiv.org/html/2607.05471v1)) [carried], and prime-rl drops samples with no trainable tokens ([prime-rl](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/algorithms.md)). The target's monitor needs a post-change soak window before it can score a slow structural change, and some runs will be preempted halfway through applying one **[I]**. Reward must therefore be written asynchronously and late, joined by episode ID, and carry a status. A half-applied action needs its own terminal state ("rolled back or not", plus a damage-check result). A censored episode must carry `reward=None`, never 0, or the trainer learns that slow changes are bad. Only async queues in the style of prime-rl or AReaL tolerate late reward, and even they are bounded by the staleness limit from Assumption 7.

## What the team must build: a control plane plus a small observation tool set

### Seven owned components

| Component | Responsibility | Which assumption it repairs |
|---|---|---|
| **Episode controller and budget plane** | Wall-clock deadline and dollar ledger in durable workflow state. Dollars are metered at a research-owned LLM proxy, reconciled with provider billing, and joined with database-side cloud billing (warehouse credits, instance-hours). Budget is reserved *before* each request, with stop-new-submissions semantics. `remaining_time` and `remaining_$` are injected every turn. A durable timer forces diagnose → optimize → report, and a fixed slice is reserved for the report. An action-duration model refuses to start actions that cannot finish in time | 3 |
| **Effect journal and reconciler** | Writes an intent record with an idempotency token before every shell or psql execution. Tool steps never retry automatically (`MaximumAttempts=1` or equivalent). On recovery, injects "outcome uncertain for command X" plus monitor-run facts (catalog diff, `pg_index.indisvalid`, postmaster start time). Model calls may retry, but their cost is always booked | 2 |
| **Persistent DB session manager** | psql sessions that persist across steps and survive server restarts, with per-subagent role or `application_name` tagging for attribution and explicit marking of cold-cache windows after a restart | 1, 2 |
| **Contention broker** | Measurement mutex, leases on objects and knobs, and non-overlap between mutating actions and measurement windows for harness-mediated tools (DBOS queue concurrency can implement it). Raw shell is observed and attributed, not blocked | 1 |
| **Effect-level monitor and reward service** | Separate principal. SQL audit tap, config and catalog diffs, an independent measurement client and workload replay, workload integrity (result equivalence), damage checks (DBA-Bench classes, durability and isolation settings), and journal-vs-effect divergence. Emits a multi-component, provenance-tagged reward, asynchronously and possibly late, with `None` for censored episodes | 4, 8 |
| **Cross-run memory and scheduler** | Harness-owned store outside the target DB, keyed by environment fingerprint. Claims from memory are labelled "declared, possibly stale" and re-grounded by fresh observation in every run. DBOS or Temporal schedules with skip-if-running overlap policy | 2 |
| **Trace writer and variant registry** | Lossless per-step record (next section) plus a `harness_variant_id` hash over prompt, tool schema, observation format, context policy and workflow | 6, 7, 8 |

### High-level tools: what exists, and the two nothing provides

The design keeps the action surface as generic shell. The high-level tools are for **setup and breadth-first observation**, so the agent spends its first minutes seeing the system rather than writing SQL against catalog views. Existing MCP servers are mostly "query plus schema" servers. Three have real diagnostic depth: Postgres MCP Pro's `analyze_db_health` (cache hit rate, connections, constraints, duplicate/unused/invalid indexes, sequence limits, vacuum, replication) ([postgres-mcp](https://github.com/crystaldba/postgres-mcp)); Google's MCP Toolbox, with the broadest multi-engine primitives (Postgres active queries, locks, `pg_settings`, query, table and replication stats; MySQL locks, fragmentation and plans), although its SQL Server and BigQuery toolsets have no monitoring primitives ([Toolbox prebuilt configs](https://mcp-toolbox.dev/documentation/configuration/prebuilt-configs/)); and pganalyze's 30-tool server, the only one with history (7 days of plans and logs, plus time series), which requires its paid collector ([pganalyze MCP](https://pganalyze.com/docs/mcp)). The best precedent for anytime triage is SQL Server's sp_BlitzFirst. It samples DMVs, waits, Perfmon and the plan cache twice over `@Seconds` (default 5) and diffs them, and separate deep-dive procedures cover cache, indexes, locks and sessions ([First Responder Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit)).

| Tool | Returns | Closest existing | Gap the harness fills |
|---|---|---|---|
| **`probe_capabilities()`** (action-space probe) | Engine, version and deployment flavour (self-managed, RDS, Aurora, Cloud SQL, Azure, Neon/Supabase, warehouse); role attributes and effective privileges on key objects; per-knob `{current, default, source, apply ∈ session / reload / restart / control-plane-only / immutable}`; installed vs. installable diagnostic extensions; control-plane rights (modify parameter group, reboot, branch); whether billing is readable | Toolbox `postgres-list-roles`, `-list-available-extensions`, `-list-pg-settings`; Azure parameter types (static/dynamic/read-only, [Azure](https://docs.azure.cn/en-us/postgresql/flexible-server/concepts-server-parameters) [snip]); AWS Billing/Pricing MCP ([awslabs/mcp](https://github.com/awslabs/mcp)) | **No tool combines these.** Read-only modes *restrict* rather than *report*. This is how the agent infers its envelope when no guardrail is supplied |
| **`triage(budget_s)`** (time-budgeted triage) | Tiered plan (e.g. 30 s / 2 min / 10 min) over the merged checklist: sessions, waits and blockers; top queries as a two-point delta; index health; vacuum, bloat and wraparound/sequences; connections; cache and I/O; replication lag and slots; backups/RPO; config anomalies; log-error classes. Each finding states its cost and what deeper tier would refine it | sp_BlitzFirst `@Seconds`; Postgres MCP Pro health check; pganalyze check-ups | **No tool takes a time budget.** This is the "10 minutes means triage" requirement made concrete |
| `workload_snapshot(window)` | Normalized per-digest calls, total/mean time, rows, reads (or bytes billed) across `pg_stat_statements`, MySQL digests, Query Store, Snowflake QUERY_HISTORY and BigQuery JOBS | Toolbox query stats; Neon `list_slow_queries` | Cross-engine normalization; staleness tags (ACCOUNT_USAGE lags by up to hours [not fetched]) |
| `activity_waits_locks()` | Running sessions, wait events, lock graph, long transactions | Toolbox active queries, locks, long-running transactions | Sampled waits need `pg_wait_sampling`, which is itself an install action |
| `config_provenance()` | Every setting with source, default, pending-restart and managed modifiability | Toolbox `list-pg-settings` (columns unconfirmed) | Joins engine provenance with control-plane modifiability |
| `maintenance_health()`, `replication_backup()` | Dead tuples, last (auto)vacuum/analyze, bloat estimates, wraparound horizon; lag, slots, RPO | Postgres MCP Pro health; sp_BlitzBackups | Engine-agnostic schema |
| `history(query)` | Prior runs' observations and applied effects for this environment fingerprint | pganalyze (SaaS collector only) | Local run-history store independent of any vendor |
| `cost_snapshot()`, `budget_status()` | DB-side spend joined to workload; remaining wall-clock and dollars, read from the budget plane | AWS Billing MCP; ClickHouse Cloud billing tool [snip] | Joins billing to per-query workload; makes the budget visible to the model |

Every observation should carry a provenance tag: source view, sampled vs. cumulative, staleness, and the privilege it required. The tools should be wrappers, not rebuilds: Toolbox for multi-engine primitives, Postgres MCP Pro's health and HypoPG logic, and sp_Blitz-style two-point sampling. Two design questions sit at the edge of "observation" and are flagged in the open questions below. Installing `pg_stat_statements` needs `shared_preload_libraries` and therefore a restart, so it is an action, not a probe [not fetched]. And creating a Neon or Aurora branch for what-if testing may break the one-environment rule.

## The harness contract that keeps the artifact trainable

The RL ecosystem has converged on two interfaces: an OpenAI-compatible endpoint with token-ID passthrough, and an episode/trajectory record. The harness should speak both and keep the environment lifecycle and reward on the research side. The contract below is the RL note's proposal, extended for this design's single environment and phase structure.

| Surface | What the harness exposes | Break it addresses |
|---|---|---|
| **Model I/O** | Every model call goes through one configurable `base_url`, with no SDK call bypassing it. Token-in/token-out or returned token IDs plus logprobs, with tokenizer and chat-template hash recorded. A retrying *model* client that survives weight-sync pauses; tool calls are never retried | T2, T5, Assumption 7 |
| **Rollout API** | `run_episode(task_spec, harness_variant_cfg, policy_endpoint, budget{wall, $}, env_binding) → episode_id`, asynchronous and resumable, with `status` and `cancel`. The trainer never touches database state | T1, T3 |
| **Environment binding** | One fixed environment per episode, declared `env_kind ∈ {prod, clone}` and `resettable: bool`, with a cache-state descriptor. For training clones only: `acquire_lease(exclusive)`, `restore(snapshot)`, `release()`. Environment-pool size, not GPU count, bounds concurrency | T4, Assumptions 1, 6 |
| **Trace schema** | Per step: `policy_version`, prompt and completion token IDs, logprobs, a loss mask (tool output = 0), and `compaction` / `subagent_call` / `continuation` edges. Per tool call: command text, idempotency key, exit status, wall time, $ cost. Per episode: phase markers (diagnose / optimize / report), `harness_variant_id`, `env_kind`, and `terminal_status ∈ {completed, budget_exhausted, preempted, harness_error, env_error, rolled_back}` | T5, T8, T9 |
| **Reward channel** | The monitor writes `reward(episode_id) = {components, provenance, confidence, available_at}` asynchronously and possibly late. Censored episodes carry `reward=None` plus a status, never 0. The monitor is unreachable from the agent's credentials | T6, Assumptions 4, 8 |
| **Algorithm defaults** | Single-rollout or critic-based advantages instead of GRPO; slow optimizer clock or per-token version-tagged off-policy correction; production episodes go only to an off-policy buffer as single samples | Assumptions 6, 7 |
| **Harness-as-parameters and offline export** | Prompt, tool schema, observation format, context policy and workflow selectable per episode, with task-level routing as in NeMo Gym. The same traces export to SFT, DPO (pairs from the same clone snapshot) and replay buffers | T7, T9 |

Training across harness variants is not optional decoration. In the Harness Scaling preprint, a single-harness Qwen3-30B policy scored 59.82 on its own harness but **46.02 on Claude Code**, and training across 18 harness configurations brought the Claude Code score to 49.62 (preprint, [arXiv 2610.29458](https://arxiv.org/html/2610.29458v1)) [carried]. Agent Lightning v1.0 reports raising Qwen3.5-35B-A3B on SWE-bench Verified from 47.8% to 61.6% with unmodified real harnesses (preprint, [arXiv 2608.17528](https://arxiv.org/abs/2608.17528)). This is why the adoption plan runs several cheap loops behind one control plane.

## Conclusion

The survey changes where the research contribution sits. The earlier round framed the contribution as a control plane wrapped around a typed DB interface and a switchable shield. With the shield removed and the action space left to the agent, the control plane has to stand in for everything the guardrail used to do implicitly. The budget plane is what makes "anytime" honest. The effect journal is what makes "learned rollback" trainable, because it turns uncertain outcomes into observations instead of silent retries. And the external monitor carries the whole safety story as well as the reward. That makes the monitor the most consequential component, not a side system: any channel it misses becomes an unpunished hack, and any reward it delays without a censoring status becomes a learned bias against slow structural change.

The second implication is about what can be published first. Every harness in the matrix fails on single-environment semantics. The first defensible result is therefore not an RL-trained agent but a measured characterization of how adopted loops (OpenHands, a mini-swe-agent fork, Claude and Codex baselines) behave against one live database when they are given an authoritative budget, an action-space probe and a budgeted triage, and when an external monitor scores them. That experiment exercises every owned component, produces the lossless multi-harness trace corpus that single-rollout and offline RL will need, and tests the eight broken assumptions empirically rather than by inference, which is the weakest point of the evidence today.
